How a skill gets used

You never invoke a skill. Each one carries a description saying what it covers and when to use it, and the agent reads the ones that match what you asked. Ask for a CREATE TABLE and it reads mariadb-create-table; ask why a query is slow and it reads mariadb-explain and mariadb-query-optimization.

That is why the output is MariaDB SQL rather than generic SQL. The skills carry the version-specific detail a model would otherwise average away — that MariaDB has a native UUID type, that utf8 means utf8mb3, that there are no functional indexes, that CREATE OR REPLACE is atomic.

The dev plugin ships all {{ site.skill_count }} of them. The smaller sql variant carries 47 — the statement, function and topical layers plus the create-script skill, but no connectors, REST or schema management.

Try them without a database

Every one of these works on a fresh install, with nothing configured. Some prompts that exercise a skill each:

Write a CREATE TABLE for a product catalogue, MariaDB style.

What changes if I move this application from MySQL to MariaDB?

How do I do semantic search in MariaDB?

Show me how to connect to MariaDB from Node.js, with a connection pool.

I need to track every change to this table for a compliance audit.

Explain what ALGORITHM=INSTANT can and cannot do on ALTER TABLE.

The fifth one is a good test of whether the skills are loaded: the answer should be system-versioned tables, a MariaDB feature with no MySQL equivalent, rather than a hand-rolled audit table with triggers.

Where they come from

Most skills are vendored from mariadb-docs agent-skills/ and keep their original licenses. The last group is maintained in this repository under additional-skills/ and is GPL-2.0. The full list of sources and their terms is in additional-skills/README.md.

Vendoring is deliberate: the skills ship inside the plugin, so the version you have is the version you tested with, and a change upstream never surprises you mid-session.
