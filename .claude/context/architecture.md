# Architecture / key decisions

[← Project Context](../PROJECT_CONTEXT.md)

## Plugins and skills

- **Five harnesses, three variants each** — `claude/`, `codex/`, `opencode/`, `hermes/` carry `dev` (all skills + MCP + LSP where supported), `sql` (SQL subset + MCP) and `contributor` (skills only, no MCP server, so no version site). `pi/` has only `dev-plugin`. Hermes adds a fourth, **`hermes/guard-plugin`** (`mariadb-guard`), the CLI guard as its own plugin, meant to be installed together with dev or sql. **Cursor** needs no plugin of its own: it installs Claude Code plugins from this repo's `.claude-plugin/marketplace.json` (Customize → + Add Marketplace → `https://github.com/mariadb/ai-plugins` → Add `dev`) into its own directory.
- **Flat skill layout everywhere** (`skills/<skill>/SKILL.md`); OpenCode discovers one dir deep. `.skills-manifest.json` uses flat paths, layer grouping preserved.
- **Skill sources**: `dev`/`sql` ← `mariadb-corporation/mariadb-docs` `agent-skills/` (manifest w/ layers). **No pinned commit** — `sync-skills.sh` defaults to the latest on the upstream default branch (`DEFAULT_REF="main"`), `$1` overrides with a tag/branch/commit; the resolved commit SHA is recorded per plugin in `skills-source.json` (`ref`="main", `commit`=the synced SHA). `contributor` ← `mariadb-shell` `.claude/skills/` (public repo; a token is still passed when available, for the API rate limit). `additional-skills/` (this repo's own) is grouped into topic subfolders — `sql/`, `rest/`, `schema-management/`, `migrator/`, `laravel/` — vendored flat into a single `additional` manifest layer. `sync-skills.sh` selects per plugin via `ADDITIONAL_SUBDIRS=(sql rest schema-management migrator laravel)` and include keys `additional-<subfolder>` (or bare `additional`=all): dev (empty include list) gets all subfolders; `sql` gets only `sql/` via `SQL_INCLUDE_LAYERS=(granular-statements granular-functions topical additional-sql)`. So every subfolder except `sql/` is dev-only. Upstream splits each connector skill into `-install` + `-usage` (dev-only).
- **Keep `skills/` to ONLY skill dirs + `.skills-manifest.json` + `skills-source.json` — no other files/dirs.** A non-skill dir (an attribution dir with `LICENSE`+`VENDORED.md`, no `SKILL.md`) makes pi's loader choke ("description is required"), and the user reports a `skills/README.md` also causes loader issues. Sources/licensing live ONLY in `additional-skills/README.md`; every plugin README's License section links to it via `../../additional-skills/README.md`, and upstream `agent-skills/topical` holds the MIT terms.
- **Tier-1 static contract** (each SKILL.md): frontmatter `name` == dir; `description` has "Use when" (≥20 chars); balanced ``` fences; any backticked `mariadb-*`/`mysql-*` under a `## See Also` heading must resolve to a real skill. `test_additional_skill_matches_its_source` makes every vendored `additional`-layer skill byte-identical to its `additional-skills/*/<name>/SKILL.md` (lookup by name; a name in two subfolders is itself a fault). Upstream-sourced skills have no local source to compare against.
- **REST skills follow the REST SQL of MariaDB Shell's built-in `mrs` module** (mariadb-shell #71 / shell-plugins #41). Metadata schema 5.0.0 renames the upstream MySQL identifiers: schema `mariadb_rest_service` (optional prefix/postfix via `CONFIGURE REST METADATA SCHEMA …`), roles `mariadb_rest_service_*`, `VENDOR MARIADB` (MySQL: `MYSQL`), tables `rest_schema`/`rest_object` (MySQL: `db_schema`/`db_object`). The serving component is the **"REST Daemon"**, the admin tool **`mariadb-shell`**. Source of truth: mariadb-shell `docs-ref/content/mariadb-rest-service/rest-sql-reference/*`; the schema project is `mysqlshdk/libs/mrs/db_schema/mariadb_rest_service.msm.project`.
- **MSM (Schema Management) skills** teach the schema lifecycle (create → develop → release → deploy) as an overview + 4 focused skills. Source: the mariadb-shell-plugins repo, `msm_plugin/lib/management.py`, `mcp_plugin/lib/msm_functions.py`, `msm_plugin/templates/`; section rules in mariadb-shell `docs-ref/content/mariadb-shell/schema-management/msm-sections.md`.
- **Laravel skills** (`additional-skills/laravel/`, dev-only, contributed by @Rhaima96, who works on MariaDB support in Laravel itself): `mariadb-laravel-connector`, `mariadb-laravel-vector`, `mariadb-laravel-ai-sdk`.
- **Plugin version ≠ shell floor.** The ai-plugins version (manifests, CHANGELOGs, `v*` tags, `docs/_config.yml` `plugin_version`; `set-plugin-version.sh`) and the `MARIADB_SHELL_VERSION` floor (launchers, MCP/LSP configs, `docs/_config.yml` `shell_floor`; `set-mariadb-shell-version.sh`) move independently; never infer one from the other. `/release [version|-] [shell-version|-]` suggests the next `YY.MM.x` from today's date and the month's tags, and the latest published shell when it is newer than the floor; anything suggested is confirmed first.
- **CLI guard**: every MCP-bearing plugin blocks a shell command that uses `mariadb`/`mysql`/`mariadb-shell`/`mysqlsh`/`mariadb-dump` for what an MCP tool covers and names the tool instead (`MARIADB_PLUGIN_ALLOW_CLI=1` turns it off) — a `PreToolUse` hook in Claude Code and Codex, the extension in Pi, `plugins/mariadb-guard.ts` in OpenCode, `hermes/guard-plugin` for Hermes. One case list, `tests/cli-guard-cases.json`, drives all implementations.

## MCP server and launchers

- `mariadb-shell` is a MySQL Shell fork. MCP tool groups: `sandbox.*`, `db.*`, `msm.*`, `util.*`, `sql.*` (+ `rest.*`/`restd.*`, deliberately undocumented — see [reference docs](docs-ref.md)).
- **Launcher** — `mariadb-mcp-launcher.{sh,cmd}`, byte-identical in the claude/codex/opencode dev+sql plugins and pi (Hermes has its own, below); edit `claude/dev-plugin/scripts/` and `cp`:
  - **Resolution order**: `$MARIADB_SHELL_BIN` → a `mariadb-shell` on `PATH` meeting the gate → a local install at `$MARIADB_SHELL_BINDIR/mariadb-shell` (default `~/.local/bin`, Windows `%LOCALAPPDATA%\Programs\mariadb-shell\bin\mariadb-shell.cmd`) → fetch+run `install.sh`/`install.ps1` from `raw.githubusercontent.com/<repo>/main/`, then launch what it installed. **No asset naming anywhere in the launcher** — the installer reads the asset list from the release's own `SHA256SUMS` and matches OS/CPU/glibc.
  - **`MARIADB_SHELL_VERSION` = minimum**, compared field-by-field numerically with `10#` base forcing (`version_ge`): `26.10.0`, `26.100.0`, `27.3.0`, `26.08.1` all pass a `26.8.0` gate; missing fields count as 0 (`26.8` passes). Windows uses `[version]$a -ge [version]$b` in PowerShell — same semantics, but stricter on two-component (`26.8` < `26.8.0`) and single-component (`27` throws → "unusable") reports, which real releases never produce.
  - **Version parse is anchored on `Ver`** (`ver\s+N(.N)+` first, bare numeric only as fallback), because the version line starts with the binary path, which may itself carry digits.
  - **stdout is sacred** (it *is* the MCP transport): every launcher message and all installer output go to stderr.
  - **Token** (`MARIADB_SHELL_TOKEN` → `GH_TOKEN` → `GITHUB_TOKEN` → `gh auth token`) is optional, exported under the name the installer reads.
  - **Prerelease: automatic fallback.** The install tries a **stable** release first and retries with `--pre-release` when there is none. `MARIADB_SHELL_PRERELEASE=1` skips straight to a prerelease, `=0` keeps the install stable-only. The `.cmd` does the same through `install.ps1`'s env var.
  - **It does NOT track the latest release.** The floor gates *accepting* what is on disk, never triggers looking for something newer: a `PATH` binary or local install at-or-above the floor is used **with no network access**. A download happens only when nothing meets the floor, and then takes the newest release (subject to `MARIADB_SHELL_TAG` and the platform's glibc/macOS version). **A floor above the newest published release costs a fetch on every server start** (the gate rejects the local copy, the installer re-fetches, the launcher warns and starts it anyway). Upgrade by raising the floor, deleting the managed install, or running `install.sh` directly.
  - **Fallback**: if the install fails but a binary exists at the target anyway (a concurrent launcher won the race), it is used with a warning; a below-gate version warns rather than refusing to start. On a slow first install it prints a stderr hint to reconnect via `/mcp`.
  - **Git-Bash/MSYS**: the `.sh` looks at the `%LOCALAPPDATA%` shim and, since `install.sh` refuses Windows, points at the `.cmd` launcher / `install.ps1`.
- **Hermes dev/sql have their own MCP launcher (#77)**, not a copy of Claude's — the Hermes catalog review required it. Install step only: exactly `v$MARIADB_SHELL_VERSION` (`MARIADB_SHELL_TAG` overrides), installer fetched from a pinned mariadb-shell commit (`INSTALLER_COMMIT`, identical in `.sh`/`.cmd`), package verified against the committed `scripts/mariadb-shell-v<floor>.SHA256SUMS` (both Hermes plugins; via the installers' `MARIADB_SHELL_SHA256SUMS`, mariadb-shell #110), no `--pre-release` retry, no `GH_TOKEN`/`gh auth token` lookup. A `MARIADB_SHELL_TAG` without committed checksums is verified against that release's own `SHA256SUMS`, with a warning. Steps 1–3 are the same as the other launchers'. The catalog's dev disclosure describes exactly this, so a floor move or `INSTALLER_COMMIT` move must reach the catalog entry (`/release` step 12). The Hermes structure test pins these properties.
- **Hermes plugin catalog (#79).** `mariadb-dev` and `mariadb-guard` are listed in `NousResearch/hermes-agent/plugin-catalog/`, each pinning an exact commit of the public `mariadb/ai-plugins` + `subdir`; the catalog never follows `main`, so a release reaches catalog users only through `/release` step 12's PR. `mariadb-sql` (a subset of dev; the reviewers list one package per product) and the contributor plugin are folder installs only.
- **Pi (pi.dev) plugin** (`pi/dev-plugin/` + **repo-root `package.json`**): a pi *extension*, not a marketplace plugin. A pi package is any dir with a `package.json` `pi` field, installed via `pi install <path|npm:…|git:…>`. **The manifest is the repo-root `package.json`** (`extensions:["./pi/dev-plugin/src/index.ts"]`, `skills:["./pi/dev-plugin/skills"]` — the skills **root**, NOT a `/*` glob: pi discovers dirs containing `SKILL.md` recursively), so the whole repo installs as one package via `pi install git:github.com/mariadb/ai-plugins`. The extension is a default-export factory (loaded by jiti, no build); its paths resolve from `import.meta.url`. **It registers the MCP server itself** (Pi 1.0): `pi.registerMcpServer("mariadb", {command: <launcher .sh, or .cmd on win32>, args: [], description})` — Pi's built-in MCP connects it at session start, so `pi install` is the whole setup. Registrations are per-session, not written to any file; a `mariadb` entry in `~/.pi/agent/mcp.json` / `.pi/mcp.json` overrides it. Default exposure is **codemode** (`tools.mcp__mariadb__<tool>(…)` from a script). Pi spawns stdio servers via cross-spawn, so the `.cmd` works on native Windows. **Never use `pi-mcp-adapter`**: any extension registering `/mcp` replaces the built-in MCP.
- **Codex — five facts that shaped the plugin** (verified against a clean `CODEX_HOME` on Codex 0.151.0):
  1. Marketplace discovery reads **`.agents/plugins/marketplace.json`**, falls back to `.claude-plugin/marketplace.json`, and **never reads `.codex-plugin/marketplace.json`** — without the `.agents/` file, `codex plugin add dev@mariadb` installs `claude/dev-plugin`. No `.codex-plugin/marketplace.json` is kept (unread; a second copy only drifts). **The per-plugin `codex/*/.codex-plugin/plugin.json` files are read**: without one the install degrades to version `local`.
  2. A plugin's `.mcp.json` must use the camelCase key **`mcpServers`**; `mcp_servers` registers **nothing**, silently.
  3. The only plugin-root placeholder Codex knows is **`${CLAUDE_PLUGIN_ROOT}`** — there is no `CODEX_PLUGIN_ROOT`.
  4. **Codex expands nothing when it spawns a plugin's MCP server.** It execs `command` verbatim, so any placeholder fails (`No such file or directory (os error 2)`); `cwd: "."` does not rescue a placeholder.
  5. **But Codex resolves a relative `cwd` against the plugin root, and a relative `command` from there** — so the codex plugins self-register with a relative extensionless `command` + `"cwd": "."`. Both halves are required. **Extensionless** serves every OS (`codex-rs/rmcp-client/src/program_resolver.rs`): on Unix the kernel uses the shebang; on Windows `which::which_in` walks `%PATHEXT%` onto the `.cmd`, and the extensionless text file is rejected by `GetBinaryType()` so it never shadows the `.cmd` (confirmed on Windows 11 ARM64 with a marker probe). Upstream issues: openai/codex #19582, #22842, #19372.
- **Claude Code's MCP connect timeout is 30 s and only `MCP_TIMEOUT` (env, ms) raises it** — per-server `timeout`/`startupTimeout`/`connectTimeout` in `.mcp.json` and `env` in a plugin's `settings.json` are ignored (probed on 2.1.304). A first start that downloads the shell can exceed it; the installer survives the launcher being killed mid-download, hence the `/mcp` reconnect hint. Documented in the Claude READMEs, DevHub get-started, docs-ref Claude Code "First Start", Troubleshooting and the Configuration Reference.
- **Claude Code and OpenCode on native Windows use extensionless launcher commands** (`scripts/mariadb-{mcp,lsp}-launcher`), which resolve through `%PATHEXT%` to the `.cmd` beside them (see gotchas for why `.sh` fails there).
- **The MCP server's multi-tenant mode** (HTTP only, API keys / OAuth2) serves only `db.*` and never `sql.*`. The launchers start a single-tenant stdio server; a server configured multi-tenant refuses stdio with a clear error. Connecting a plugin to a shared multi-tenant server would be new MCP wiring (HTTP transport + bearer token in the manifests).

## SQL language server

- **`mariadb-lsp`** ships next to `mariadb-shell` in every release package from 26.10.3 (Windows too; the native `.deb`/`.rpm` don't have it). `mariadb-lsp lsp` speaks LSP over stdio. Registered only where a harness supports it: **Claude** plugin `.lsp.json` (dev + sql; LSP tool behind `ENABLE_LSP_TOOL=1`), **OpenCode** an `lsp` block in `opencode.json` (which also turns OpenCode's built-in servers on), **Hermes** a user-added `lsp.servers` entry in `config.yaml` (plugins can't register one; README has the snippet with `warmup_timeout: 240`). **Codex and pi have no LSP support** — they get the MCP server's `sql.*` tools instead.
- `mariadb-lsp-launcher.{sh,cmd}` (identical in claude/opencode/hermes × dev/sql) **never installs**: it resolves the shell exactly as the MCP launcher does and runs the `mariadb-lsp` beside it (beside the link, then beside its target); with no shell yet it **waits** for the MCP launcher's install (`MARIADB_LSP_WAIT`, default 180 s), then falls back to any `mariadb-lsp` on PATH/BINDIR; `MARIADB_LSP_BIN` overrides. It never compares `mariadb-lsp --version` with the floor — that is lsp-server's own version.
- **The MCP server's `sql.*` group** (shell ≥ 26.10.3; mariadb-shell-plugins #63/#65) — `sql.check`, `sql.outline`, `sql.format` run `mariadb-lsp check|outline|format` on inline SQL or a `file_path` (allowed paths; MSM `SOURCE` includes expanded by the server, then `--no-source`), no database. Registered only where `mariadb-lsp` is found (`mcp setup --lspPath`, next to the running shell, PATH, `~/.local/bin`).
- **Won't fix (user's decision), so don't re-raise in reviews:** (1) the LSP launcher waits for the MCP launcher's install before falling back to a `mariadb-lsp` on PATH, even when one is there — preferring the `mariadb-lsp` paired with the shell is the design; (2) the clean-install helpers (`_clean_path`, `SUFFIXES`, env setup) are copied across the claude/opencode/hermes LSP e2e tests — the suites stay isolated on purpose.

## Tests

- **One suite per harness** (`*/dev-plugin-test*/`), tiers `static` (default), `db` (default), `eval`, `e2e` (opt-in). Suites stay isolated: `lib/` helpers are copied, not shared. Tests live **beside** the plugin, never inside it (`pi install` would ship them).
- **Unified runner**: repo-root `run_tests.py` runs every suite with the Python inside `mariadb-shell` (`mariadb-shell --pym pytest`), one pytest process per suite, with one combined coverage report (`npm test`, `test:static|db|eval|e2e`). **CI does not use it**: `.github/workflows/*-test.yml` call `setup-python` + a per-suite `pytest`, because GitHub runners have no `mariadb-shell`; the per-suite `pyproject.toml` files stay authoritative there.
- **The db tier self-provisions a sandbox**: `lib/sandbox.py` deploys an instance on a free port via the MCP server's `sandbox.deploy`, then `stop`+`delete` in a `finally`. Any of `MARIADB_HOST/PORT/USER/PASSWORD` set → that server is used instead (CI's service container); unreachable → skip.
- **e2e tests** drive the real agent CLI **once** in a module-scoped `workflow` fixture, then assert side effects in separate `test_stepN_*` tests (runnable via `pytest -k stepN`). Claude: REST, MSM, LSP; Codex: REST, MSM; Hermes: install + skills + one MCP call, LSP; OpenCode: LSP; pi: skills + one MCP call.
- **REST e2e**: spins up a real sandbox; teardown in the fixture `finally` (runs even on timeout). `SHOW REST` are mariadb-shell DDL extensions → run via the MCP server (`_rest_via_show`, discovers the SQL tool from `tools/list`), with a `mariadb_rest_service` PyMySQL fallback.
- **MSM e2e**: **no DB/sandbox** — `msm.prepare_release`/`generate_deployment_script` are pure on-disk ops. Drives the agent through **two releases** (v1.0.0 → develop → v1.1.0) and asserts the right sections were used (tables in create-140 / update-240, views in the snapshot's 150), the **update script was filled** (comments stripped so the empty template can't pass), and the v1.1.0 deployment script composes **all** objects. Hermetic: points the shell config home at a throwaway dir and pre-seeds its allow-list.
- **Codex e2e**: skills arrive **only via an installed plugin**, so fixtures install from `REPO_ROOT` into a throwaway `CODEX_HOME` with the real `auth.json` copied in; **`--dangerously-bypass-approvals-and-sandbox` is mandatory** (otherwise every MCP call is auto-cancelled); evidence is JSONL `item.completed` events with `item.type == "mcp_tool_call"`; the injected launcher is a wrapper that touches a marker then execs the real one, proving *this plugin's* launcher was spawned.
- **Pi suite**: no `eval` tier (pi has no SDK; driving the `pi` binary *is* the behavioural test). Pi-specific static tests guard the wiring that has broken before: root `package.json` `pi` field with resolvable paths, skills entry = root not glob, `skills/` holding only skill dirs + manifests, `pi-mcp-adapter` NOT declared, `src/index.ts` default export calling `registerMcpServer` for `mariadb` with both launchers. e2e runs with a throwaway `PI_CODING_AGENT_DIR` (`pi_cli.isolated_agent_dir()`); the prompt **pins two tables** and forbids connecting to a database; the MCP test hands the model an exact codemode script calling `tools.mcp__mariadb__db_list_connections({})` and asserts on Pi's `tool_execution_end` events (`result.details.server == "mariadb"`), not on the model's words.
- **LSP e2e from a clean install** (Claude, Hermes, OpenCode): empty `MARIADB_SHELL_BINDIR`/`PREFIX`, PATH stripped of every dir holding `mariadb-shell`/`mariadb-lsp`.

## DevHub (`docs/`)

- The user-facing site, GitHub Pages' own Jekyll from `main` + `/docs`, served at **`ai-plugins.mariadb.org`** (`docs/CNAME` + `url:`, `baseurl: ""`) by the fork's Pages. **No build step, no theme gem, no plugins beyond the Pages allow-list** (`jekyll-seo-tag`, `jekyll-sitemap`). Tutorials are a Jekyll collection (`docs/_tutorials/`, filename = URL slug, front matter drives card/filters/pager).
- **Generated data**: `docs/_data/skills.yml` and `skill_count` in `docs/_config.yml`, by `docs/regenerate-skills-data.py` from the vendored manifests — **`sync-skills.sh` runs it as its final step** (soft dependency on python3: warns instead of failing). `plugin_version` is set by `set-plugin-version.sh`, `shell_floor` by `set-mariadb-shell-version.sh`; `tool_count` and `mariadb_baseline` are hand-maintained. `docs/_data/downloads.yml` lists sandbox server packages for the offline-install page; `/release` updates the download links.
- **Visual design = mariadb.org's twentytwentyfive-child theme**: its light palette (`#F7F8F0` / `#355872` / `#7AAACE` / `#9CD5FF`, accent `#964A2C`) and dark mode (`#1B3C53` / `#F3E9DD` / `#D2C1B6` / `#456882` / `#D08C72`) in the `--ch-*` tokens, every text colour ≥4.5:1; Manrope variable font (Google Fonts `wght@200..800`), `letter-spacing: -0.1px` on body, `-webkit-font-smoothing` left at auto (`antialiased` made links look thinner than mariadb.org's). Hero = mariadb.org's 135deg primary→secondary gradient + a left scrim; primary button = its `#F08A5D` "Download" button, hover `#F5A07B`. Page layout is a port of `devhub.gridgain.com`'s. Code blocks use the **One Dark** prism palette in both themes.
- **Header** (user's layout): 88px row of logo (MariaDB Foundation: light `mariadb_foundation_h.svg` / dark `mariadb_foundation_inv_h.svg`; favicon = its seal mark), links left-aligned, GitHub + mariadb.org's pill theme switch. 600–939px: 150px logo, links on one line under it. ≤599px: ☰ opens mariadb.org's left drawer (Esc/backdrop/✕ close, body scroll locked). Breakpoints measured with ~17px scrollbar margin. **Footer** = mariadb.org's simplified one (Learn / Reference / Project columns, logo right, tagline under a hairline).
- **The DevHub points at the `mariadb` org on purpose** (`repo: https://github.com/mariadb/ai-plugins`): community issues and PRs go to the fork — see [repo conventions](repo-conventions.md).
- **The hero code panels are sized by the PANEL, not the viewport, so their responsive rules are container queries** (`.hero-panel` has `container-type: inline-size`; the inset drops to 0 below 480px of panel) — see the gotcha on panel width. A scroll affordance (`…` marker + fade) shows while code is hidden; `site.js` toggles `.is-clipped`.
- `docs/serve.sh` is the local preview (`npm run docs{,:open,:build,:skills}`).
