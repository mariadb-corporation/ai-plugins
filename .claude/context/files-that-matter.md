## Skills

- `additional-skills/rest/mariadb-rest-service-create/SKILL.md` -> CONFIGURE REST METADATA → CREATE REST SERVICE/SCHEMA → REST VIEW (GraphQL block, @KEY/@SORTABLE/@UNNEST/CRUD) + REST PROCEDURE/FUNCTION.
- `additional-skills/rest/mariadb-rest-service-{update-endpoints,authorization,show,drop}/SKILL.md` -> ALTER; auth apps/users/roles + GRANT/REVOKE REST; SHOW REST / SHOW CREATE REST; DROP REST.
- `additional-skills/schema-management/mariadb-schema-management{,-create,-develop,-release,-deploy}/SKILL.md` -> MSM lifecycle (overview + 4 steps; `-create` asks for native `UUID NOT NULL DEFAULT UUID_v7()` primary keys on client-facing tables, never `CHAR(36)`; `-develop` documents SOURCE breakout files; `-release` the fill-update-then-generate order).
- `additional-skills/sql/mariadb-schema-create-script/SKILL.md` -> standalone (non-MSM) create-script conventions; the e2e Start-Block assertion.
- `additional-skills/README.md` -> the single sources & licensing doc for the vendored skills; external skills licensed per their origin repos, `additional-skills/` ones GPL-2.0. Every plugin README that ships skills links to it.
- `scripts/sync-skills.sh` -> vendors skills; `ADDITIONAL_SUBDIRS` + `SQL_INCLUDE_LAYERS` drive per-plugin subfolder selection — **a new subfolder must be added to `ADDITIONAL_SUBDIRS` or its skills are silently never vendored**; `TARGET_PLUGINS` lists every plugin that gets skills; rerun after editing `additional-skills/`. Regenerates the DevHub skill data last. Does NOT copy any README into `skills/`.

## Launchers and manifests

- `*/{dev,sql}-plugin/scripts/mariadb-mcp-launcher.{sh,cmd}` (+ extensionless shim) -> identical in claude/codex/opencode/pi; edit `claude/dev-plugin/scripts/` and `cp`, then check with `shasum`. `.gitattributes` keeps `.cmd` CRLF.
- `hermes/{dev,sql}-plugin/scripts/mariadb-mcp-launcher.{sh,cmd}` + `mariadb-shell-v<floor>.SHA256SUMS` -> Hermes' own launcher (pinned `INSTALLER_COMMIT`, committed checksums); both Hermes plugins carry the same files.
- `*/{dev,sql}-plugin/scripts/mariadb-lsp-launcher.{sh,cmd}` (claude/opencode/hermes) -> the LSP launcher; edit `claude/dev-plugin/scripts/` and copy. `test_lsp_launcher_is_the_shared_launcher` checks the copies, `test_lsp_launcher_never_installs` that it has no installer code.
- `claude/{dev,sql}-plugin/.lsp.json` -> registers `mariadb` for `.sql` via the launcher, `startupTimeout: 240000`. The object is **strict** — an unknown key makes Claude reject the whole file, and `claude plugin validate` doesn't read it — so `test_lsp_json_registers_the_launcher` pins the allowed keys.
- `.agents/plugins/marketplace.json` -> Codex's marketplace; `.claude-plugin/marketplace.json` -> Claude Code's (also what Cursor reads).
- `package.json` (repo root) -> the pi manifest: `pi` field pointing into `pi/dev-plugin/` (no dependencies), plus npm scripts. `pi/dev-plugin/src/index.ts` -> the factory extension (`pi.registerMcpServer("mariadb", …)` + CLI guard). `pi/README.md` -> how pi loads the extensions.

## Version scripts

- `scripts/set-plugin-version.sh` -> the plugin **package** version: every plugin manifest (`plugin.json`, Hermes `plugin.yaml` incl. the guard), each README's `Version **x.y.z**` line, the repo-root `package.json` and `docs/_config.yml` `plugin_version`. Its JSON substitution is anchored to line start, not `/g` (`package.json` has other version strings). CHANGELOG history untouched.
- `scripts/set-mariadb-shell-version.sh` -> the only way to move the floor: `MARIADB_SHELL_VERSION` across launchers, `.mcp.json`, `opencode.json`, `.lsp.json`, `setup-codex-mcp.{sh,cmd}`'s `SHELL_VERSION=`, `docs/_config.yml` `shell_floor`, two docs-ref sites, and the READMEs' `` `MARIADB_SHELL_VERSION` (default `<v>`) `` prose — **that prose shape must stay on one line** or the perl substitution stops matching. It downloads the new release's `SHA256SUMS` into both Hermes plugins and stops before editing anything when that release is not published. Its "N file(s)" is the number scanned, not changed. **Check its reach whenever a file gains a version site** — it has lagged new files repeatedly.

## Tests

- `run_tests.py` (repo root) -> the unified runner: auto-discovers suites via `*/dev-plugin-test*/conftest.py`, resolves the shell from `--shell`/`$MARIADB_SHELL`/PATH, installs each suite's `requirements.txt` into the shell's Python (`--no-install` to skip), runs **one pytest process per suite** (same-named modules + `lib` packages collide in one process), passes ALL selected suite dirs as `--cov` with `--cov-append` so the last suite's reports are the combined ones. `pytest-coverage.ini` (passed via `-c`, so it **replaces** the per-suite `pyproject.toml` → keep the markers + `-m "not eval and not e2e"` default in sync); `.coveragerc` measures only `lib/` + `conftest.py`. Reports in `test-results/` + `htmlcov/`, gitignored. `--` splits pytest passthrough args.
- `*/dev-plugin-test*/lib/{mcp_stdio.py,skills.py}` + `test_structure.py` -> MCP stdio client + tier-1 static contract, incl. `test_additional_skill_matches_its_source` (helpers `additional_skills()` / `additional_sources()`). `mcp_stdio.py` answers server-initiated requests with a JSON-RPC error (an unanswerable elicitation would hang), keeps stderr in a temp file, and never leaks the shell subprocess when the handshake fails.
- `*/dev-plugin-test*/lib/sandbox.py` (identical in every suite) -> the db tier's sandbox: `deployed_sandbox()` context manager; `SandboxUnavailable` → skip, a failed deploy → error. `_prepare_config_home()` makes an isolated shell config home that **carries the plugins** (symlinks every plugin from the real config home, `~/.mariadb-shell`) and writes `plugin_data/mcp_plugin/settings.json` with `allowedPaths=[sandbox_dir]` — **without the allow-list entry the deploy HANGS**.
- `*/dev-plugin-test*/test_db_connect.py` (db tier, one per suite) -> the only coverage of `db.connect` and of the connection `sandbox.deploy` registers. Uses `sandbox.mcp_client()` so the client runs on the instance's own config home (the registration lives in that config home's secret store). Pins both halves of the URI contract: equivalent spellings are accepted; a uri asking for **more** (`/schema`, `?ssl-mode=REQUIRED`) is refused.
- `claude/dev-plugin-tests/test_mcp_launcher.py` (static) -> step 4 of the POSIX MCP launcher, parametrized over the shared and the Hermes launcher: a stub `curl` serves a fake install.sh that fails when another one is unpacking (as tar did), stub shells print `STARTED <ver>` on stdout. Covers one install, three at once, a killed lock holder, a harness-stopped launcher, failed installs, install.sh's lock, the wait timeout, the LSP launcher during a locked install, and a shell printing messages before its `Ver` line. `test_structure.py`'s `test_cmd_launcher_clears_psmodulepath_before_powershell` guards the `.cmd` side.
- `claude/dev-plugin-tests/manual/test_cmd_launchers_concurrent.ps1` (manual, Windows, not CI) -> starts the `.cmd` launchers as a client does (stdin/stdout piped, stderr to a file), speaks MCP (`initialize` + `tools/list`) and LSP (`initialize`), checks stdout is protocol only and the prefix holds one version folder. Scenarios `two`, `three` (+ LSP launcher, + a late launcher that must not install), `kill` (tree killed mid-install), `orphan` (only cmd.exe killed). `-Src` another plugin's scripts (Hermes), `-InstallerRef refs/heads/<branch>` a mariadb-shell branch's install.ps1. Run under both `powershell` and `pwsh`; described in the suite README.
- `claude/dev-plugin-tests/test_e2e_claude.py` -> REST e2e: fixture `workflow` + `test_step0..5`; helpers `_rest_via_show`, `_rest_via_metadata`, `_parse_rest_paths`, `_find_sql_tool`, `_teardown_sandbox`.
- `claude/dev-plugin-tests/test_e2e_msm_claude.py` -> MSM e2e: helpers `_find_project`, `_sections` (split on `^-- MSM Section NNN:` banners), `_strip_sql_comments`, `_seed_allowed_path`.
- `claude/dev-plugin-tests/test_e2e_lsp_claude.py`, `hermes/dev-plugin-tests/test_e2e_lsp_hermes.py`, `opencode/dev-plugin-test/test_e2e_lsp_opencode.py` -> clean-install LSP e2e: Claude's `LSP` tool lists the tables / Hermes' `write_file` result carries mariadb `lsp_diagnostics` / `opencode debug lsp diagnostics` (step 3 needs `E2E_OPENCODE_MODEL`). `hermes/dev-plugin-tests/lib/hermes_cli.py` has `install_plugin(mcp_env=…)` and `run_hermes(env=…)`.
- `codex/dev-plugin-test/lib/codex_cli.py` -> codex e2e wiring; `_path_spellings` seeds every macOS temp-path variant.
- `pi/dev-plugin-tests/lib/pi_cli.py` -> all pi-specific wiring (`missing_prerequisite`, `provider_ready` round-trip gate, `isolated_agent_dir`, `install_package`, `run_pi` with `--approve --mode json`, JSONL parsing incl. `assistant_text()`/`model()`/`mcp_tool_results()`).
- `tests/cli-guard-cases.json` -> the one case list every CLI-guard implementation is tested against.

## DevHub

- `docs/` -> `_config.yml` (`url` + `baseurl` environment-specific; `skill_count` GENERATED; `plugin_version`/`shell_floor` set by the scripts), `_tutorials/`, `_data/{nav,paths,skills,downloads}.yml` (`skills.yml` GENERATED), `_layouts/`, `_includes/{navbar,footer,head,…}.html`, `serve.sh`, `regenerate-skills-data.py`, `README.md` (publishing, adding a tutorial).
- `docs/assets/css/style.css` -> the whole design system. Colour lives ONLY in the two `--ch-*` token blocks; the hero card and its panels add local `--card-*` properties. Blocks worth knowing: `.btn--primary` (filled button + crossfade hover overlay, needs `isolation: isolate`), `.hero__bg`, `.hero__card` (gradient border + blooms, `z-index`-sensitive), `.hero-panel`/`.hero-panel__body`/`.hero-code` (container query + cut-off marker).
- `docs/assets/js/site.js` -> progressive enhancement only, ES5 style, every feature guarded: theme toggle (binds every `[data-theme-toggle]`, never an id), menu drawer, TOC, tutorial filters, hero code cut-off marker. `?v={{ site.time }}` on style.css/site.js busts stale browser caches.
- `docs/_data/nav.yml` -> header links, one `{title,url[,match]}` per entry; `match` only for sections whose children must stay highlighted.
- `docs/CNAME` -> `ai-plugins.mariadb.org`, the only host; `_config.yml`'s `url:` matches it.
- `docs/.markdownlint.jsonc`, `docs-ref/content/.markdownlint.jsonc` -> per-folder markdownlint exceptions. The docs-ref one sits above the synced folder, so it never reaches mariadb-docs.

Takes `$ARGUMENTS` and splits it itself (see gotchas). `<version>` must sort above the latest `v*` tag; `[shell-version]` must be a published mariadb-shell release. Keep it in step with the scripts and with `repo-conventions.md`.
